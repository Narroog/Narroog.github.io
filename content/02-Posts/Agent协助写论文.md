## 引子

上周，我只用了 3 天时间，借助codex，在只有idea，无数据、无图的情况下，完成了一篇8页左右的会议论文。正所谓实践出真知，这三天的集中工作，正是使用Agent协助写论文的最佳实践，我收获颇丰。

本文结合这次实践，总结一套 Agent 协助写论文的工作流程。



## 工作流程概览

整个流程可以分为三个阶段：

| 阶段 | 目标 | 关键任务 |
| --- | --- | --- |
| 准备资料 | 便于Agent生成一个“有模有样”的论文 | 准备大纲、模板、参考资料、数据和图片 |
| 生成草稿 | 获得格式规范、内容基本完整的第一版论文 | 撰写提示词，限定资料来源、输出位置和未完成内容的标记方式 |
| 迭代润色 | 逐步改善逻辑、图表、表述和格式 | 人机高效效作，润色论文 |

## 1. 准备资料

当前的 Agent 已经能够直接读取工作区中的文件。因此，在开始写作之前，最重要的工作不是立即编写一段很长的提示词，而是先把资料准备好。

我建议至少准备以下内容：

- **大纲**：最重要的资料，用来规定引言逻辑、正文结构、图表安排和主要结论。
- **模板**：目标期刊或会议提供的 LaTeX 或 Word 模板，用来限定版式和文件结构。
- **参考资料**：与研究内容相关的论文、PPT、方法说明，以及目标期刊或会议中的同领域论文。
- **原始数据**：用于生成线图、分布图或云图的可追溯数据。
- **已有图片**：已经完成的示意图、实验照片和其他不适合由 Agent 自动生成的图像。

### 大纲应该写到什么程度？

大纲就像一棵树的主干：它不需要包含所有细节，但必须决定内容将向哪里生长。一份可供参考的大纲如下：

```markdown
# 标题
# 0 引言
## 背景与研究问题（可参考 xx）
## 当前研究的不足（可参考 xx）
## 本文的主要工作（可参考 xx）
# 1 方法（可参考 xx）
## 1.1 xx
Fig. 1. 图题 1
## 1.2 xx
Fig. 2. 图题 2
# 2 结果与讨论
## 2.1 xx
Fig. x. 图题 x
## 2.2 xx
Fig. n. 图题 n
# 3 结论
## 结论 1
## 结论 2
```

引言和结论最好写得详细一些，因为它们决定了论文的主要故事。对于正文，可以先列出子标题、每节要回答的问题，以及预计使用的图表。如果某一节需要借鉴特定资料，应在对应位置直接标明文件名。

### 如何组织工作区？

资料最好按用途分类，避免 Agent 在大量无关文件中反复搜索。原始数据可放在Origin_Data/中，已有图片放在Figure/中。在Writing/工作区内，大纲可放在draft/中，模版放在templete/中，其余参考资料可放在reference/中。例如：

```text
workspace/
├── Original_Data/
├── Figure/
└── Writing/
    ├── draft/
    │   ├── 大纲.md
    │   ├── v0/
    │   ├── v1/
    │   └── ...
    ├── template/
    └── reference/
```

## 2. 生成草稿

资料准备完成后，提示词反而可以很简短。它只需要说清四件事：任务是什么、依据什么资料、应输出到哪里，以及如何处理缺失内容。

如果图片已经准备完成，可以使用下面这类提示词：

```text
请在 Writing/ 文件夹内撰写论文草稿。
依据 Writing/draft/大纲.md 组织内容，并使用 Writing/template/ 中的论文模板。
Writing/reference/ 中包含参考资料和目标会议的同领域论文，可参考其写作风格和格式。
大纲中要求的图片位于 Figure/ 文件夹。
请将第一版草稿输出到 Writing/draft/v0/ 中。
```

如果部分图表尚未完成，可以要求 Agent 根据原始数据生成。对于原始数据缺失的情况，可以让Agent使用占位的数据生成图片，以便先检查版式和叙事结构。对应的补充提示可以写成：

```text
大纲中要求的部分图片需要生成。
请根据 Original_Data/ 中的原始数据绘图，并按需使用 Figure/ 中的已有图片。
如果原始数据无法支持某幅图，请保留明确的占位标记，说明所需数据，不得将模拟或占位数据表述为真实研究结果。
```

## 3. 迭代润色

我们不能要求Agent第一版就能达到可以发表的水平。接下来的关键，是建立一套人和 Agent 都容易理解的修改机制。

我会让 Agent 在每次生成草稿时，同时维护一份 `逐段内容.md`。它是大纲的升级版，包含每个层级的主要内容、与上一版相比的改动，以及供作者填写的修改意见。

```markdown
# 标题
# 相对于上一版的改动
# 整体修改意见
# 逐段内容
## 章节标题
- 主要内容：xxxx
- 修改意见：

### 第 x 段｜xxxx
- 主要内容：xxxx
- 修改意见：

### Fig. x. 图题 x
- 修改意见：
```

这样做有两个好处。

第一，作者可以先阅读每段的内容摘要，快速检查论文的整体逻辑，不必在早期阶段就反复逐句通读全文。

第二，修改意见可以被精确地放在全文、章节、段落或图表层级下。Agent 不需要猜测修改对象，也可以减少在长文档中搜索和定位的成本。

### 分版本安排修改重点

每一个大版本最好只聚焦一类问题，避免在同一轮中同时改逻辑、数据、图表和句子，导致修改目标混乱。一个可供参考的顺序是：

| 版本 | 主要修改目标 |
| --- | --- |
| v1 | 引言的逻辑、图片内容的安排、主要结论 |
| v2 | 引言的表述、图表的科学性、段落之间的逻辑 |
| v3 | 段落内部的逻辑、图表的可读性与美观性 |
| v4 | 句子表述的科学性和一致性 |
| v5 | 版式、引用、参考文献和投稿要求 |

每个大版本下还可以保留多个小版本，用来比较不同修改方案。但无论迭代多少次，都应该保留原始数据、生成脚本和版本变化记录，让图表和结论始终可以追溯。
